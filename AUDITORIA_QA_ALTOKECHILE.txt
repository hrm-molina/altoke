CRIT-01: ALMACENAMIENTO DE CONTRASEÑAS EN BASE64 (NO HASHEADO)
----------------------------------------------------------------
Archivo: src/lib/db.ts:95
Código:
  password_hash: user.password ? btoa(user.password) : user.password_hash || ""

Riesgo: Base64 es codificación, NO hashing. Cualquiera con acceso de lectura a
la BD obtiene todas las contraseñas en texto plano. Incumple Ley 19.628 Art. 10
(medidas de seguridad) y mejores prácticas OWASP.

Solución Requerida:
  - Migrar a Supabase Auth (bcrypt/argon2 nativo)
  - O implementar Edge Function con bcrypt/argon2
  - NUNCA almacenar contraseñas en localStorage ni BD sin hash cryptográfico

CRIT-02: POLÍTICAS RLS COMPLETAMENTE ABIERTAS (TRUE EN TODO)
----------------------------------------------------------------
Archivo: supabase/schema.sql:255-287
Problema: Todas las políticas usan `USING (TRUE)` y `WITH CHECK (TRUE)`

Tablas afectadas:
  - usuarios: SELECT, INSERT, UPDATE, DELETE sin restricción
  - servicios: SELECT, INSERT, UPDATE, DELETE sin restricción
  - calificaciones: SELECT, INSERT sin restricción
  - alertas: ALL sin restricción

Riesgo: Cualquier usuario anónimo (anon key) puede:
  - Leer TODOS los emails, RUTs, teléfonos, fechas de nacimiento, contraseñas
  - Modificar/borrar CUALQUIER registro de CUALQUIER usuario
  - Insertar reseñas falsas, manipular ratings, spam de alertas

Solución Requerida (Ejemplo usuarios):
  CREATE POLICY "Usuario ve solo su perfil" ON public.usuarios
    FOR SELECT USING (auth.uid() = id);
  CREATE POLICY "Usuario actualiza solo su perfil" ON public.usuarios
    FOR UPDATE USING (auth.uid() = id);
  CREATE POLICY "Usuario elimina solo su cuenta" ON public.usuarios
    FOR DELETE USING (auth.uid() = id);

Y equivalentemente para servicios (prestador_id = auth.uid()), etc.

CRIT-03: AUSENCIA TOTAL DE RATE LIMITING / PROTECCIÓN BRUTE FORCE
------------------------------------------------------------------
Endpoints vulnerables:
  - Login: Intentos ilimitados, sin CAPTCHA, sin lockout
  - Registro: Sin verificación de email, sin prevención duplicados a nivel BD
  - Contacto: Formulario mailto: directo (cosecha de emails, spam)

Riesgo: Ataques de diccionario, credential stuffing, enumeración de usuarios,
abuso de formularios. Incumple principio de seguridad por defecto.

Solución Requerida:
  - Middleware Next.js o Edge Function con rate limiting (ej: 5 req/min/IP)
  - CAPTCHA (hCaptcha/turnstile) en login/registro
  - Verificación de email obligatoria antes de activar cuenta
  - Reemplazar mailto: por Edge Function + Resend/SendGrid

💡 RECOMENDACIÓN ARQUITECTÓNICA ESTRATÉGICA
================================================================================

ELIMINAR AUTH PERSONALIZADO COMPLETAMENTE → USAR SUPABASE AUTH + RLS PROPIO

Razones:
  1. Supabase Auth maneja: bcrypt/argon2, email verify, password reset,
     sesiones JWT, refresh tokens, social login, MFA
  2. auth.uid() permite RLS perfecto sin lógica custom
  3. Reduce superficie ataque: menos código = menos bugs
  4. Cumple Ley 19.628 "medidas técnicas adecuadas" por defecto
  5. Listo para escalar: 100k+ usuarios sin cambios

Migración:
  - Mantener localStorage solo para cache UI (no auth)
  - Sincronizar perfiles usuarios tabla pública via trigger auth.users
  - Usar supabase.auth.onAuthStateChange() para estado sesión
